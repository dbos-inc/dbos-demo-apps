DBOS adds durable execution to your applications, checkpointing their workflows and steps to Postgres. If your apps ever crash, DBOS recovers them from their last completed steps.

Try it: launch a workflow, then crash this app. When you restart, the workflow always resumes from exactly where it left off.

main.rs 
async fn example_workflow(_: ()) -> dbos::Result<String> {dbos::step("step_one", step_one).await?;dbos::step("step_two", step_two).await?;dbos::step("step_three", step_three).await?;} async fn step_one() -> dbos::Result<()> {tokio::time::sleep(STEP_DURATION).await;println!("Completed step 1!");Ok(())} async fn step_two() -> dbos::Result<()> {tokio::time::sleep(STEP_DURATION).await;println!("Completed step 2!");Ok(())} async fn step_three() -> dbos::Result<()> {tokio::time::sleep(STEP_DURATION).await;println!("Completed step 3!");Ok(())}

DBOS durable workflows can be started on a cron-style schedule. The schedule can be adjusted while the app is running. A pause takes effect at the next tick, and other changes may take up to 30 seconds to propagate.

Try it: press Apply to start the schedule, and watch the runs add up. A schedule is a row in the database, so it is still running after a restart.

main.rs

DBOS queues let you run workflow fan-outs and control concurrency. The worker_concurrency parameter controls how many workflows one process may run simultaneously.

Try it: press "Enqueue 5 workflows" repeatedly to put workflows on the queue. Three run at a time and the rest wait — then change the limit and press Apply, without restarting the app.

main.rs 
async fn enqueued_workflow(_: ()) -> dbos::Result<String> {println!("Enqueued workflow starting.");dbos::sleep(STEP_DURATION).await?;println!("Enqueued workflow ending.");} dbos.register_queue("demo-queue", QueueOptions {worker_concurrency: Some(3),..Default::default()}, QueueConflict::NeverUpdate).await?; enqueued.start_with((), StartOptions {queue: Some(QueueRequest::new("demo-queue")),..Default::default()}).await?;

A workflow publishes events — named values anyone can read by key, from outside the workflow, in another process, or after it has finished.

Try it: start an order, then immediately press Read on shipped. The request blocks until the workflow gets there and publishes it — no polling, and nothing held open on the workflow's side.

main.rs 
async fn order_workflow(_: ()) -> dbos::Result<String> {for key in ["accepted", "charged", "shipped"] {dbos::sleep(ORDER_STEP).await?;dbos::set_event(key, &value).await?;}} // A read that waits, from outside any workflow.let shipped: Option<String> = dbos.get_event(&id, "shipped", Duration::from_secs(12)).await?;

A workflow can stop and wait to be told something. recv parks it durably — nothing of it stays in memory, and a message sent later, by any process, wakes it.

Try it: start a few approval requests and watch them wait. Approve one, or approve them all at once — send_bulk is a single transaction, so nobody is approved unless everybody is. You can also crash the app on the Workflows tab first: the requests are still waiting when it comes back.

main.rs 
async fn approval_workflow(_: ()) -> dbos::Result<String> {let decision: Option<String> =dbos::recv(Some("approval"), APPROVAL_TIMEOUT).await?;Ok(decision.unwrap_or_else(|| "expired".to_owned()))} // One waiting workflow.dbos.send_with(SendMessage {    topic: Some("approval"),    ..SendMessage::new(&id, &decision)},SendOptions::default(),).await?; // Every waiting workflow, in one transaction.dbos.send_bulk(&messages).await?;
